# AGENTS.md — Design Computer

Guidance for AI agents and contributors working on Design Computer.
Status: **DRAFT**. Items marked `[OPEN]` are undecided; don't treat them as settled. Settled decisions are in the decision log (§15).

---

## 1. The mental model (read this first)

> **A design is a shared, ordered, attributed stream of intent, applied to a deterministic geometry engine. The file is that history. The GUI, scripts, AI agents and remote collaborators are all clients of it.**

Traditional CAD keeps a mutable model inside one application. The GUI is the only real interface, and automation (macros, "AI features") is bolted on from outside. Design Computer inverts this: the model lives behind a protocol, and the GUI is just the first client.

### Three pillars

1. **Intent is the source of truth.** We store what someone *meant* ("extrude this profile 12 mm"), not the resulting geometry. Geometry is a deterministic, rebuildable consequence of intent. This makes files robust across kernel versions, history inspectable, and changes reviewable and mergeable.
2. **One kind of participant.** Humans, agents, scripts and remote users are all **actors** that submit commands to one **authority**. Attribution, permissions, undo and audit are built once, for everyone. Collaboration is "more actors", not a second mechanism.
3. **Nothing is hidden.** Everything a human sees has a structured, queryable form with stable IDs. Humans and agents see the same design. Neither has a privileged view.

### Ideas that follow from the pillars

- **Proposals are the universal way to change a design.** A proposal is a pending set of commands with a visual and structural diff. It covers an agent's risky edit, a colleague's suggestion, design review, branching and version history. A direct commit is the case where the actor's permissions allow auto-accept. In solo use, proposals are invisible.
- **Design intent is first-class data.** Features and constraints can carry *why* ("clearance hole for M6 bolt", "mating face with bracket"), not only *what*. Humans benefit, and agents benefit most: they can reason about purpose instead of guessing from shapes. See §9.
- **A determinism contract.** The same commands produce the same model on every supported machine. This underpins sync, caching and stable IDs. See §4.5.
- **Durable vs ephemeral state.** The log holds only committed intent. Dragging, previews, cursors and camera travel on a separate live channel that agents can also observe.
- **Errors, conflicts and unresolved references are data**, with entity IDs and suggested fixes. Failures are local and visible, never silent.

**The architecture must be invisible to the user.** They get the fast, direct-manipulation feel of a great CAD tool. The mental model is how the system is built, not something they must learn.

## 2. Purpose, goals, scope

Design Computer is a cross-platform (Linux, macOS, Windows; **desktop only, no browser target**) parametric CAD system, **agent-native from day one**.

**Problem:** There is no CAD tool that is both truly performant and truly cross-platform. FreeCAD is the main open option, but it is slow on non-trivial models, has a fragile recompute model and topological naming problem, and is frustrating to use.

**Target domain:** mechanical parts: machine design and product design. The architecture must stay extensible to other domains (architecture, electronics enclosures, CAM, simulation) via feature/plugin registration, not kernel forks.

**Goals (priority order):**
1. **Responsiveness and scale.** 60 fps+ viewport; edits feel instant; UI never blocks on geometry work; **very large designs and assemblies (100k+ component instances) are a first-class target** (§10a), not an afterthought.
2. **Robustness.** Booleans, fillets and rebuilds don't fail mysteriously; when they fail, the error is clear and local.
3. **Usability.** Discoverable, consistent, keyboard-friendly, good defaults.
4. **Portability.** One codebase, identical results on every OS.
5. **Openness.** Open formats, scriptable, no lock-in.

**Non-goals (for now):** web/browser target, CAM, FEA/simulation, photorealistic rendering, PLM, collaboration features. Design so they can be added (see §8); don't build them.

## 3. Hard constraints

- **No OpenCascade (OCCT)**, and no other pre-existing CAD kernel (Parasolid, ACIS, CGAL-as-kernel, Manifold-as-kernel, etc.). The geometry kernel, constraint solver and feature/history engine are written in-house.
- **No wrapping or building on existing CAD applications** (FreeCAD, Blender, etc.).
- **Foundational libraries are allowed** where not CAD-specific: windowing, GPU abstraction, basic linear algebra, image decoding, font shaping, compression, serialization, testing. Prefer small, well-maintained, permissively licensed crates. Justify each new dependency in the commit that adds it.
- Reading/writing interchange formats (STEP, IGES, STL, 3MF, DXF, glTF) is our own code. Generic container/markup parsers (zip, XML) are fine.

## 4. Core contracts

These are architectural rules. Violating them is a bug, even if the feature "works".

### 4.1 Commands and queries (one way in, one way out)
- Every mutation is a named, typed, serializable `Command` (e.g. `sketch.add_line`, `feature.extrude`, `param.set`). The GUI, shortcuts, scripts, agents and remote users all use it. **The GUI never mutates the document directly.**
- Every piece of state a human sees has a structured, queryable form: feature tree, sketch entities and constraints, DOF/conflict status, parameters, selection, errors with the geometry they refer to, measurements, mass properties, bounding boxes, units, camera state.
- **Done means:** a feature works through the command layer and its state is visible through the query layer. UI-only features are bugs.

### 4.2 Actors, authority, revisions
- Every command carries: `actor` (`human:<id>` / `agent:<name>` / `script` / `remote:<id>`), `base_revision`, target entity IDs, optional expected values (preconditions, e.g. "depth was 10"), and a globally unique command ID.
- An **authority** component validates, orders and applies commands, then emits events to all subscribers. Single-user mode uses the same pipeline with an in-process authority and one actor. Real collaboration only adds transport and actors.
- **Capabilities per actor:** read-only, propose-only, scoped to certain features/entities, or full. Default for agents is configurable and conservative.
- **Transactions:** commands can be grouped atomically, dry-run (returns resulting state/diff without committing), and undone. Undo is per actor by default. Agent actions appear in the same history, attributed.

### 4.3 Command granularity (what is "one command")
Three levels:
- **Gesture** (dragging, scrubbing, live preview): ephemeral, never logged. Streams on the live channel; coalesced.
- **Command** (the atomic unit): one semantic user intent, one undo step, one reviewable change. **Test: can a designer describe it in one sentence?** ("Add a 20 mm circle", "Set depth to 12".) Not "move point 0.001 mm".
- **Transaction:** a named group of commands ("Create mounting bracket").

Log hygiene: consecutive same-actor edits to the same target within a short window are coalesced at commit; checkpoints are written into the log periodically so replay doesn't grow unbounded. High-level commands (e.g. `sketch.add_rectangle`) log as themselves; their expansion into primitives is deterministic and not stored.

### 4.4 Visual and semantic parity
- **Visual:** agents can request what the human sees: renders from any camera (shaded, wireframe, section, multi-view), with optional labelled overlays (face/edge IDs, dimensions, constraint glyphs). Rendering works headless.
- **Semantic:** the kernel's exact knowledge is available as data: topology graph, surface/curve types and parameters, adjacency, tolerances. Don't make agents infer from pixels what the kernel knows exactly. See §10 (agent query layer).
- **Stable references:** entities have persistent IDs usable in commands and queries across rebuilds and sessions.
- **Errors are data:** structured diagnostics (code, message, entity IDs, suggested fixes), identical to what the human sees.

### 4.5 Determinism contract
Same command log → same model, bit-for-bit where required, on every supported OS/CPU (x86_64 and aarch64 on Linux, macOS, Windows). Rules for kernel/solver/feature code:
- **No fast-math; no implicit fused-multiply-add.** Use FMA only where explicitly chosen and identical on all targets.
- **No platform libm.** Standard-library transcendentals (`sin`, `cos`, `exp`, `pow`, ...) may differ across platforms. Kernel code uses a pure-Rust deterministic implementation (e.g. the `libm` crate or our own); enforce with clippy `disallowed_methods`.
- **Fixed evaluation order.** No parallel reductions whose result depends on scheduling; parallelism only over independent work with deterministic merge order.
- **Deterministic collections.** No iteration over default-hashed `HashMap`/`HashSet` in results; use ordered or deterministic-hasher structures.
- **IDs come from commands and structure, not float comparisons.** Entity IDs derive from (creating command ID, structural role), so tiny numeric differences can't change names.
- **State hashes.** Each log entry carries a hash of the resulting model state (canonicalized). Hashes are **incremental and hierarchical (Merkle-style: per feature, per document, per assembly node)** so a command only rehashes what it touched, never the whole model (§10a). Replicas compare hashes; a mismatch is detected immediately and triggers resync from the authority instead of silently diverging.
- **CI proof.** A cross-platform golden-hash test suite runs on all supported OS/CPU targets on every change to kernel code.

### 4.6 Durable vs ephemeral
- **Durable (log):** committed commands.
- **Ephemeral (live channel):** gesture streams, previews, cursors, selection, camera, presence ("Alex is editing Sketch2"). Not stored; observable by agents.

### 4.7 Scale contracts (summary; details in §10a)
- **Definitions vs instances.** Geometry is defined once; assemblies place instances (definition reference + transform). Nothing duplicates geometry per instance, in memory, on the GPU, or on disk.
- **References, not embedding.** Documents refer to other documents by stable ID + content hash. Unresolved references are a first-class state, not an error.
- **Work is proportional to what changed or what is visible,** never to model size: incremental recompute with early cutoff, incremental hashing, lazy loading, culling/LOD, scoped and paginated queries.
- **Every query, event and render path must be bounded** (pagination, hierarchy, interest management). Unbounded "give me everything" calls are not allowed in the protocol.

## 5. Architecture `[OPEN]` (proposed)

Language: **Rust** (memory safety without GC pauses, safe parallelism, single toolchain on all OSes).

Layered workspace; dependencies point downward only:

```
app/            egui shell, windowing, input, command palette (issues commands, renders queries)
  ui/           widgets, panels, theming
  viewport/     camera, picking, selection, gizmos, overlays
protocol/       command/query schema, JSON-RPC server, MCP server, headless runner (schema generated from Rust types)
authority/      actors, capabilities, ordering, revisions, proposals, events, live channel
document/       document state, feature tree, undo/redo, intent annotations, persistence, versioning
assembly/       definitions, instances, component tree, mates, load levels, configurations, simplified reps, spatial index (BVH)
store/          project store: resolves cross-document references, content-addressed cache, lazy/streamed loading, checkpoints
features/       registry + sketch, extrude, revolve, sweep, loft, fillet, chamfer, shell, pattern, ...
solver/         2D/3D geometric constraint solver (own)
kernel/         B-rep topology + geometry (own)
  geom/         line, arc, conic, B-spline/NURBS, plane, cylinder, cone, sphere, torus
  topo/         vertex/edge/loop/face/shell/solid
  ops/          booleans, offset, fillet, intersection, projection, healing
  validate/     validity checker run on every operation result (see §11)
  tess/         adaptive tessellation, cached by geometry hash
  robust/       exact/adaptive-precision predicates, tolerance policy
math/           vectors, matrices, intervals, polynomial roots, deterministic numerics
render/         wgpu renderer: GPU instancing, hierarchical culling, LOD, batched edges, ID-buffer picking; headless-capable (designed for scale from the first version, §10a)
io/             native format, STL, 3MF, STEP, DXF, glTF
```

Rules:
- `kernel/`, `solver/`, `features/`, `document/`, `authority/` have **no UI or GPU dependencies** and run headless and in tests.
- The kernel API is pure: operations take immutable inputs and return new shapes (persistent/shared data). This enables undo, caching and safe parallelism.
- Geometry work runs on a job system off the UI thread; results are versioned and stale results are discarded.
- **No global singletons;** document and authority state are explicit values so multiple documents/sessions coexist.
- **Feature registry:** features are registered types with parameter schema, rebuild function, UI hints, docs and (optional) intent schema. Plugins add features the same way. Files store feature type IDs + versions. Plugin boundary (native vs WASM plugins) is `[OPEN]` until the first plugin is needed.

## 7. Native file format (`.dcad`)

STL/STEP/3MF are **export/interchange only**. The native format is the only lossless one (features, sketches, constraints, parameters, intent, persistent IDs, actor history).

- **Source of truth = command log.** `history.jsonl` is a deterministic, one-command-per-line text log (actor, timestamp, IDs, state hash). Readable by humans and agents without the app. Text is for transparency and debugging; it is **not** a git merge strategy. The format serves in-app operation-level sync and versioning (§8).
- **Cache is disposable.** `cache/` holds B-rep, tessellation, thumbnail. Missing, stale, or kernel-mismatched → rebuild from log. A file never becomes unreadable because the kernel changed.
- **Container:** zip with `manifest.json` (format version, per-feature type+version, kernel version, units, external references), `history.jsonl`, `parameters.json`, `intent.json`, `cache/`, `thumbnail.png`.
- **One document per part/subassembly, not one giant file.** Assemblies reference other documents by stable ID + content hash; the project store resolves them. Missing or changed references become *unresolved*, never fatal.
- **Checkpoints.** Each log contains periodic checkpoints (full state snapshots) so opening never replays full history; the cache is the normal open path, replay is the fallback.
- **LOD cache.** The cache holds multiple tessellation LODs and a bounding volume per definition, so assemblies can open in lightweight form without touching the B-rep (§10a).
- **Forward compatibility:** unknown feature types (e.g. missing plugin) are preserved verbatim and shown as unresolved, never dropped. Format changes ship with migrations and tests against archived sample files.
- **Safety:** atomic saves (temp file + rename); append-only autosave journal for crash recovery.
- **Determinism:** same model → byte-identical serialization (stable ordering, normalized floats).
- **Extensibility:** namespaced per-plugin entries; reserved space for collaboration metadata (authors, branches, proposals).
- Milestone 1: write/read log, manifest, thumbnail, rebuild-on-open. Cache follows once the kernel has something worth caching.

## 8. Collaboration plan (future; design for it now, build later)

Collaboration is a custom, CAD-aware feature built on the actor/authority model (§4.2). **Not git, not generic text merging, not a CRDT over the feature tree.**

- **Central sequencer.** One authority gives each command a total order. The "server" can be a user's app, a team server, or the local process. Peers replay deterministic commands and verify state hashes (§4.5).
- **Why not CRDT/OT over the tree:** CAD edits are structured and interdependent; automatic merging can produce a model that is valid as data but nonsensical as a design. Explicit conflict rules are safer and more explainable.
- **Conflict rules (model-level):**
  - Same parameter edited concurrently → authority order wins; the loser is notified with both values.
  - Reference to a deleted entity → the dependent feature becomes **unresolved** (flagged, repairable), never silently dropped or rejected.
  - Concurrent sketch edits → soft claims/presence ("Alex is editing Sketch2") discourage collision; if it still happens, constraint conflicts are surfaced as data.
  - Preconditions in commands catch stale edits before they apply.
- **Proposals and branches** are the review mechanism: pending command sets with a structural + visual diff, acceptance by someone with the capability. Named versions and branches are in-app features on the log.
- **Live channel** carries presence, cursors, selections, previews (§4.6) — durable log stays small.
- **Agents are teammates.** An agent can propose, review or edit exactly as a remote colleague would, under its capabilities.
- **Not now:** sync transport, accounts, servers. What must hold now: commands carry actor/revision/preconditions, IDs are globally unique, state hashes exist, authority is a component.

## 9. Design intent layer

Geometry records what; intent records why. Optional, structured, stored in `intent.json`, attached to entity IDs:
- **Purpose tags:** `clearance_hole(M6)`, `mating_face(bracket_A)`, `datum`, `load_bearing`, `cosmetic`.
- **Requirements and checks:** `min_wall_thickness ≥ 2 mm`, `hole_spacing = 50 ± 0.1`. Checks are evaluable through queries and report pass/fail with offending entities.
- **Relations:** design-level links ("these four holes pattern around the bore").
- **Authorship:** who/what asserted the intent (human or agent) and when.

Agents read intent to understand purpose, and write it to explain their work. Humans get it as notes, filters ("show all mating faces") and automated checks. The kernel never depends on intent; it is metadata over stable IDs.

## 10. Agent query layer (spatial understanding)

Agents are only as good as what they can ask. Beyond raw topology, provide:
- **Selectors by predicate:** `faces where type=planar and normal≈+Z and area>100`; `edges of face F where type=circle`. Results are stable-ID lists.
- **Relations:** coaxial, parallel, perpendicular, tangent, offset distance, symmetric, patterned — computed exactly by the kernel.
- **Feature-level summaries:** deterministic text description of the model ("Block 80×40×20 with 4 through-holes Ø6 on top face, pattern spacing 60×20"). Generated from the feature tree plus geometry, not by a language model.
- **Spatial queries:** point/ray containment and hit, distance and clearance between entities, interference, min/max wall thickness, bounding box, mass properties.
- **Verification queries:** run intent checks (§9), manufacturability checks, and "what changed" diffs between revisions.
- **Render with legend:** multi-view and section renders with entity-ID overlays and a machine-readable legend mapping labels to IDs.
- **Scale-aware by design:** all queries are scoped (by component, subtree, region or selector), paginated and bounded. Large models are explored **hierarchically**: summaries per subassembly ("Gearbox: 412 parts, bbox …, 3 unresolved refs"), then drill down. Events are deltas filtered by interest (what the actor subscribed to or can see). See §10a.
- **Agent benchmark ("agent gym"):** a suite of tasks (build this part from a description, fix this failing feature, make this change without breaking X) scored automatically. Run in CI. Add a task whenever an agent struggles. This is how we know the query layer is good enough.

## 10a. Scale and large assemblies

Target: designs and assemblies with **100k+ component instances**, interactive on a modern workstation. Numbers below are proposed budgets `[OPEN]`, tracked in CI.

| Budget | Target |
|---|---|
| Open 100k-instance assembly to interactive lightweight view | < 5 s |
| Navigation with LOD, tens of millions of visible triangles | 60 fps |
| Edit a part in context | responsive, no full-assembly rebuild |
| Memory | scales with number of distinct definitions, not instances |
| Any single query/event | bounded size and latency |

### Data model
- **Definition vs instance.** A *definition* (part or subassembly) holds geometry/features once. An *instance* = definition ID + transform + per-instance overrides (appearance, configuration, suppression). Patterns generate instances, never copied geometry. One definition is tessellated once and drawn many times.
- **Component tree.** An assembly is a tree of instances with mates. Instance IDs are hierarchical and stable (path of instance IDs), so references and intent survive reordering.
- **Cross-document references.** By stable ID + content hash, resolved through `store/`. Version pinning and update policy (follow latest / pinned) are per reference. Missing/changed → *unresolved* state (§8 semantics).
- **Configurations and simplified representations.** Variants of a definition (sizes, options) and cheap substitutes (envelope/shrink-wrap/bounding outline) for large or purchased components, selectable per instance or per assembly view.
- **Compact layout.** Index-based storage (arenas, `u32` IDs, structure-of-arrays) in hot paths; avoid pointer-heavy object graphs; memory budgets per subsystem.

### Load levels (per component, per session)
1. **Unloaded:** name, transform, bounding box only.
2. **Lightweight:** cached LOD mesh, no B-rep.
3. **Resolved:** full B-rep, read-only (measurement, exact queries, section views).
4. **Editable:** feature tree live and rebuildable.

Loading is lazy and demand-driven (visibility, queries, edits) and may be streamed in the background. Only the part being edited requires the kernel and history replay. Agents and humans can request level changes via commands/queries, and every query result states the load level it was computed from.

### Compute
- **Early cutoff.** A part's *interface hash* (geometry other parts depend on) determines whether dependents rebuild. If it didn't change, nothing downstream runs.
- **Parallel, deterministic rebuild.** Independent definitions rebuild in parallel; results merge in deterministic order (§4.5).
- **Content-addressed caches.** Tessellation, mass properties, bounding volumes and other derived data are cached by content hash and shared across instances and documents.
- **Spatial index.** Hierarchical BVH over instances and within definitions, for picking, culling, interference, clearance and region queries. Updated incrementally.
- **Assembly solving.** Mates form a graph; decompose into rigid subassemblies and flexible clusters; solve only the affected cluster while dragging; full re-solve is explicit and rare.

### Rendering (design in from the first renderer)
- GPU instancing with per-instance transform/state buffers.
- Hierarchical frustum culling, then occlusion culling; LOD selection by projected size.
- Later: clustered (meshlet-style) LODs streamed on demand for very large single parts.
- Batched edge/silhouette rendering; ID buffer for picking; out-of-core streaming with a GPU memory budget.
- Headless renders (agent parity) use the same scalable path and support isolate, section, and region-of-interest views.

### Protocol, agents and collaboration at scale
- Queries are **scoped, paginated, bounded**; hierarchical summaries come first, detail on request. Streaming results where useful.
- Events are **deltas filtered by interest** (subscription to subtrees/regions/visible set); the live channel follows the same rule.
- Authority state is partitioned by document/subtree, so unrelated edits don't contend; per-document ordering with cross-document references versioned by hash.
- Incremental Merkle hashes (§4.5) make verification cost proportional to what changed.

### Proof
- **Synthetic assembly generator** producing 1k / 10k / 100k / 1M-instance assemblies (varied depth, repetition, mates) used in benchmarks and tests.
- CI tracks open time, navigation frame time, edit-in-context latency, memory, query latency at each size. Regressions block merges like any other hot-path regression (§13).

## 11. Known risks and mitigations

| Risk | Mitigation |
|---|---|
| **Kernel robustness** (booleans, fillets, tolerance). No architecture rescues a kernel that fails. | **Never corrupt, always explain.** Every kernel op is transactional and its result passes `kernel/validate` (manifold, orientation, Euler characteristic, no self-intersection, positive volume) before it is accepted; failure rolls back and returns a structured error. Ops declare which surface-type pairs they support and return `Unsupported` otherwise. Start with a small, tiered scope (planar → quadrics → NURBS). One tolerance policy. Exact predicates. Differential tests against analytic ground truth, property-based and fuzz tests, and a growing hard-case corpus. CI tracks **success rate on the corpus** as a headline metric; it must never drop. |
| **Cross-platform determinism** | The contract in §4.5: deterministic math, ordered collections, fixed reduction order, IDs from structure, per-revision state hashes, golden-hash CI on all OS/CPU targets. A mismatch is detected, not silent. |
| **Command granularity** | Gesture/command/transaction levels (§4.3), coalescing, checkpoints. "One sentence" test for every new command. |
| **UX becoming over-abstract** | Architecture is invisible: solo mode auto-accepts, proposals/actors appear only when relevant. **Concept budget:** basic modeling requires no concept beyond sketch, constraint, feature, parameter. **Workflow benchmarks:** timed tasks (e.g. model a bracket with holes and fillets) compared to SolidWorks/Fusion workflows; regression-tracked. Dogfood: every milestone ends with modeling a real part. Performance budgets enforced in CI (§12). |
| **Agent spatial understanding** | Semantic query layer + intent layer (§9, §10), exact kernel data instead of pixels, labelled renders, agent gym benchmark in CI. |
| **Scale (large assemblies)** | Decide the structural pieces now (definition/instance model, cross-document references, load levels, checkpoints, incremental hashes, instancing/LOD-capable renderer, compact data layout) and build the heavy machinery later (§10a). Synthetic assembly generator + scale benchmarks in CI from the first milestone so regressions are caught while cheap. All protocol surfaces are bounded and hierarchical. |
| **Scope creep from a big idea** | Milestones stay small and shippable (§13). The mental model is carried by contracts (§4), not by building every future feature now. |

## 12. UX principles and practices

1. **Never block.** Long operations are async, show progress, and are cancellable.
2. **Direct manipulation first.** Drag faces/edges/dimensions; live preview while editing parameters (gesture channel, §4.3).
3. **Command palette everywhere.** Fuzzy search over every command with its shortcut shown. Every action is a bindable, scriptable command.
4. **Fast sketch → feature flow.** Auto-constraint inference, instant DOF feedback (color coding), snapping with clear indicators, dimension by typing.
5. **Errors are local and actionable.** A failed feature marks itself, explains why, highlights the offending geometry, and doesn't poison unrelated features.
6. **Undo is total and cheap**, per actor.
7. **Predictable defaults, deep customization.** Navigation presets (SolidWorks/Fusion/Onshape/Blender-style), themes, high-DPI, accessible contrast, keyboard-only operation.
8. **No modal workbenches.** One coherent environment with context-sensitive tools.
9. **Performance budgets:** navigation input→pixel < 16 ms; typical parameter edit recompute < 100 ms on mid-size parts; benchmarked in CI.
10. **Agents are visible, not intrusive.** Show who/what made each change, allow review via proposals, never take control of the user's interaction state.

## 13. Engineering practices

- **Testing:** unit tests per kernel op; property-based tests (watertightness, Euler characteristic, volume conservation under booleans); hard-case corpus (tangent/coincident faces, degenerate geometry, tiny features); analytic cross-checks.
- **Benchmarks:** `criterion` for tessellation, booleans, solver, recompute; CI tracks regressions. No >5% regression in a hot path without justification.
- **Scale benchmarks:** synthetic assemblies of increasing size (§10a); every hot path states its complexity in terms of *changed* or *visible* items, not total model size.
- **Fuzzing:** importers, protocol parser, kernel ops.
- **Robustness over cleverness:** prefer a simple algorithm that handles degenerate input correctly; add fast paths afterward, guarded by tests.
- **No panics across the kernel boundary;** return typed errors with context.
- **Docs:** each kernel algorithm gets a short design note in `docs/kernel/` citing the method or paper.
- **Style:** `rustfmt` + `clippy` clean; small modules; explicit units (mm default); no global mutable state.
- **Dependencies:** minimal, audited (`cargo deny`), permissive licenses only (MIT/Apache-2.0/BSD/zlib).
- **Schemas:** protocol and file-format schemas are generated from Rust types and versioned; breaking changes require migration and sample-file tests.

Decisions and lessons: (1) one structural naming rule for the boolean and the layered model (`dc-kernel::naming`): a piece of a split face is `<base>#<hash of its outer-loop neighbours>`, duplicate edges likewise, and the boolean's output is canonically ordered; (2) the first scheme gave the biggest piece the plain name, which would flip when a cut moved across the middle, so every piece gets a suffix and the old name is refused (with the pieces listed) rather than guessed; (3) the layered model's `#<n>` and `@<region>` suffixes (enumeration order) were replaced by the same rule; (4) hash suffixes are stable but opaque.
- 2026-10-10: Phase F (features on the B-rep; note `docs/kernel/features-on-brep.md`). Decisions and lessons: (1) fillet and chamfer of straight edges between flat faces are local B-rep surgery (new edges on both faces, a cylinder or plane between, arcs where the end faces are cut), not a boolean, because a fillet cylinder is tangent to the faces it blends and tangent contact is exactly what the boolean refuses; (2) edges along the axis of a layered part still go to the layered model (names, rims), everything else to the surgery, and a part rounded by surgery has no layered model; (3) partial revolve builds the caps and walls directly and derives every face's orientation from one choice plus the shared-edge rule; (4) shell is only for prisms: the cavity is the end outline moved inwards, subtracted with the boolean; (5) loft and sweep exist for straight edges only and are made with commands (no page yet), and a second sketch became a real dependency (`FeatureSpec::sketches()`); (6) bugs found by tests I wrote strictly: a shell offset went the wrong way because it used the line's parameter direction instead of the direction of travel, and a smoke script was flaky because it clicked before the view had finished fitting.
- 2026-10-10: Phase G (3D selection). Decisions and lessons: (1) a selection is a list (`AppState::selection()`) with the one chosen last as the primary (`selected`, which panels and commands still read); code that sets `selected` directly drops the rest, so nothing that predates the list can see stale extras; (2) Ctrl+click adds or takes out, Ctrl+drag draws a selection box (to the right takes what is wholly inside, to the left what it touches, Shift adds), done in `dc_render::box_hits` so the rule is testable without a window and an agent can ask for the same set; only what can be seen is taken (a sample test through the picker), sketch lines wherever they are; (3) drilling down is a mode (`select.feature_first`, off by default, so SolidWorks-style direct picking stays the default): the first click on a part picks the feature, a click inside it picks the face or edge; (4) selected edges become a fillet's edges and selected end faces a shell's openings, several selected features are deleted in one undo step; (5) scripted pointer events carry modifiers on the button event, not in the platform's modifier state, so the viewport remembers the modifiers of the last pointer button event; the first live test showed Ctrl+drag orbiting the view because of this and every logic test had passed.
- 2026-10-10: Loft and Sweep pages; layered-model retirement measured, not done. Decisions and lessons: (1) Loft and Sweep are pages like the others (`FeatureKind::Loft/Sweep`, second sketch and path line chosen on the page, ribbon buttons, icons, edit from the tree) and send the same `feature.loft/sweep` commands; (2) `revolve_full` builds a full revolve straight as a B-rep (cylinders with a seam, flat rings) and is differentially tested against the layered revolve (volume, area, bounds, face names, watertight mesh) but is **not wired in yet**; (3) I tried switching extrude/revolve to build without the layered model: about a dozen tests failed, for real reasons: a cut on a rim-rounded part needs cones and tori in the boolean, a cut that keeps only what is inside the profile has no boolean path, a shell and some edge rounds behave differently on the boolean's faces, and face names differ; so retiring it needs those four things first (listed in TASKS.md), and the experiment was reverted; (4) cross-drilled holes need the intersection of two non-parallel cylinders, a space curve the kernel has no curve type for; they stay refused; (5) a picker whose triangle test had exact bounds left a crack on shared mesh edges: in a window of one particular shape a hidden edge crossed a front edge exactly at its middle, the ray saw through and the hidden edge was selected by a box; found only by the live smoke test, fixed with a tiny barycentric slack and covered by a test at that window size.

### Testing the UI (agents)
- The app is instrumented with `eguidev` (MIT; widgets tagged by id, state published as the `app` diagnostic). Build with `--features devtools` to attach the runtime; `.edev.toml` does this. `edev mcp` is registered for Claude Code in `.mcp.json`; the skill `.claude/skills/eguidev` lists the ids and the workflow. Smoke scripts live in `smoketest/` and run with `xvfb-run -a edev smoke` (also on a real display).
- 2026-10-10: Decision: use `eguidev`/`edev`, not `egui-mcp(-client)`: that one targets egui 0.33 (it would force a downgrade of the whole app) and only injects coordinates, while eguidev gives widget ids, state, fixtures and Luau smoke tests on egui 0.35. It needs Rust 1.95+ (its Luau runtime uses `if let` guards), so the toolchain was updated from 1.94.1 to stable (1.99.0) with the user's approval. `devtools` is off by default: the release app carries only the inert tags and does not read or write the user's saved settings while it is on.
